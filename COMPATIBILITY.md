## Architecture and limits at baseline

| Area | Baseline and impact |
| --- | --- |
| App | `ios/Sources` uses a SwiftUI session shell with Metal framebuffer presentation, USB tablet and keyboard controls, and a Safari/OAuth sheet. The Objective-C bridge locates one prepared VM in `Documents/Machines/Win11`, with a legacy Documents root fallback. The Duo-oriented hinge integration and fixed laptop layout heuristics are in `HingeSensorView.swift`, `VMViewModel.swift` and `SessionView.swift`. |
| Engine | `core` runs ARM64-to-ARM64 DBT, a 4 KiB guest software MMU, ASID-aware caches and Windows Prism-compatible translation. `host/winvm.c` owns a singleton board, threads, disks and device resources. In-process switching or restart needs lifecycle and cleanup work before exposing those controls. |
| Devices | `devices/winvirt.c` and `devices/acpi.c` wire the UEFI/ACPI board, GIC, up to two raw NVMe disks, xHCI HID, HDA and VirtIO-Net. The iOS bridge attaches only disk 0. The board has no ISO optical drive, USB storage installer or implemented vTPM. Input and framebuffer behavior should be checked on non-folding devices. Metal presents a framebuffer. |
| RAM limits | The TXM helper in `winios_jit.c` tries 4608 down to 2048 MiB and reserves 2560 MiB of physical headroom before trying a candidate. The bridge otherwise estimates 2048–4096 MiB from process headroom. `winvm.c` defaults to 4096 MiB. `winvirt.c` maps guest RAM starting at PA `0x40000000`, below ECAM at `0x4010000000`, with 64-bit sizes. The board may use upstream Mach entry ownership, file-backed RAM with prefault, or anonymous mapping. OS memory accounting and page commitment can fail separately from reserving address space. |
| CPU limits | iOS compiles with a four-vCPU cap in `core/machine.h`. The bridge uses all four. The desktop engine has an eight-vCPU cap. |
| JIT limits | iOS requests 384 MiB and reserves a corresponding low-address hole in the executable's zero-fill section. TXM rejects RX mappings above `0x7000000000`. It also needs an RW alias and an executable self-test at both ends. The desktop default is 768 MiB. Cache metadata scales with capacity. Dispatch and translation check the signed 26-bit branch displacement and have indirect paths. Audit placement, reachability, address widths, ledger commitment and full flush behavior before lifting the iOS cap. A larger cache reservation does not establish that the OS can commit it under load. |
| Firmware and storage | The two 64 MiB pflash banks take external `code.fd` and writable `vars.fd`. Each VM requires its own NVRAM. NVMe consumes raw disks. HVSPARSE packs only nonzero runs and expands to a sparse raw file. The current app supports a prepared disk with those files, and the compatibility path recognizes raw disks of at least 64 MiB. |
| Signing and deployment | The original XcodeGen spec and device scripts assumed a personal team, signing identity, profile, bundle ID and device identifiers. The fork uses `io.github.hazerbvisor.windowsios-ez` and accepts external signing settings and a supplied device ID. XcodeGen and the Makefile retain iOS 17.0. Actual debugger and memory capabilities depend on the signature, provisioned entitlements and OS. |

The target is a physical ARM64 iPad Air M4 on iPadOS 27.0.1, with 12 GB as the owner-supplied test assumption. Use the reported physical memory when recording test results. The 10 GiB + 1536 MiB configuration reported for Henge is a test target for WindowsiOS-ez. Its executable reservation, physical RAM and process footprint require separate measurements. The app now saves Automatic, Compatibility, Balanced, Performance, Experimental and Custom settings. It checks the actual RAM request against physical memory, process headroom and available upstream preallocation. The Compatibility preset still requests 384 MiB. The executable now provides a 1536 MiB zero-fill hold on the low address range, following Henge. The allocator releases the hold immediately before the authorized debugger requests the selected mapping. iOS 26 and later can request larger mappings up to the 1536 MiB experimental preset. `WINIOS_JIT_HOLD_BYTES` can tune the maximum hold in a diagnostic build. Virtual reservation size and resident memory are reported separately. An existing smaller mapping cannot be grown during the session. The debugger allocation, RX address limit and executable self-test still govern whether a request succeeds. Reload the app between guest sessions until the singleton engine supports full teardown.

## Installer audit

`scripts/provision_windows_arm64.py` assumes a specific Microsoft ARM64 ESD at a local path. It uses desktop `wimlib-imagex`, `hdiutil`, `diskutil`, Homebrew QEMU EDK2 firmware and a local signed virtio-win NetKVM driver directory. It stages FAT32 WinPE plus an exFAT partition holding an unsplit install WIM on the second NVMe disk. Windows PE partitions the target, runs DISM and BCDBOOT, and injects the network driver. The script then boots the installed disk through a second phase.

The same script also patches security and OOBE settings, creates a personal autologon administrator and embeds a Duo computer name. `optimize_windows_lite.py` applies further offline security and registry changes. A new installer must use a security-preserving provisioning flow and validate Secure Boot and Windows 11 TPM requirements against this board. The immediate on-device blocker is construction of an EDK2-bootable GPT installer disk with a Windows PE image and signed drivers from legitimate media, followed by verified guest progress and shutdown signals. The app streams the ISO into a sparse GPT installer with a FAT32 EFI partition and a separate exFAT payload partition. It changes only the WinPE startup configuration in its temporary boot.wim copy. The startup script locates the payload and launches Microsoft Setup with `/InstallFrom` and optional `/InstallDrivers`. The guest handles signature checks, account setup and activation. With a selected edition, active automation is limited to a verified blank disk on its first boot. The app uses an answer file with `WillWipeDisk=false` and disarms it before a guest reboot. Actual boot and installation, including Setup hardware requirements, still need a physical device.

Microsoft's public ARM64 ISO page currently advertises 26H2. Keep the baseline on build 26100 and use legitimately obtained 24H2 media when Microsoft does not offer a public 24H2 ARM64 link. Home and Pro 24H2 servicing ended October 13, 2026. Enterprise and Education 24H2 servicing ends October 12, 2027. ## Windows Setup and DISM recovery

WinPE boots from a FAT32 EFI partition. The read-only exFAT partition contains the ARM64 `sources/setup.exe`, its adjacent source files, and one unsplit WIM or ESD. The launcher validates the paths, uses the stock Setup UI for disk selection, and records the signed decimal process exit code. It saves WinPE Panther logs before starting background collection of Panther and SetupAPI logs from other volumes. It uses a separate 128 MiB FAT32 GPT disk when WinPE assigns it a drive letter. DiskPart enumeration is available from the recovery prompt and does not run synchronously during launch. The launcher's **M** option retries stock Setup without optional edition or driver flags.

The VM's primary NVMe serial is `WIN11IOS01`, the read-only Setup media is `WIN11INST`, and the diagnostics disk is `WINIOSLOG`. PCI order establishes these host identities. Windows disk numbers are assigned by Windows. The generated answer file preselects only the edition and includes no DiskPart commands, firmware policy changes or Windows security bypasses. The launched WinPE snapshot and its logs still need review on the target device. [Windows Setup options](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-command-line-options) · [Setup log locations](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-log-files-and-event-logs)

The upstream DISM and BCDBOOT sequence can form a separate backend. It would need to identify the target by a verified disk identity and obtain explicit confirmation before partition writes, then apply the selected image, add the signed driver, and run BCDBOOT against the identified EFI partition. The old script guesses a disk by size, falls back to disk 0, runs `clean`, and edits offline registry policy. Those behaviors are unsuitable for recovery. The current recovery path uses stock Setup.

## NVMe and EFI access investigation

The reported iPad run extracted Windows files to `E:`. `mountvol` assigned `F:` to an EFI partition, but directory reads and DiskPart enumeration stopped responding. WinPE and other guest work stayed responsive. `mountvol` identifying a volume does not demonstrate that FAT directory reads can finish. The Setup image already has its own read-only ESP. A drive letter alone cannot tell which controller owns the mounted partition. The BCD status `0xc0000098` establishes a boot-configuration failure, but the original logs and an NVMe trace are needed to distinguish an inaccessible ESP from an invalid BCD store.

`devices/nvme.c`, `devices/pcie.c`, `devices/gicv3.c`, `host/disk.c` and `devices/pflash.c` were unchanged from upstream `0071d697` before this repair. Upstream supported two NVMe controllers, and its DISM and BCDBOOT workflow used a separate installer image. This fork places stock Setup media on the second controller and adds a writable logging disk on the third. It also added host-side disarming of the answer file at warm restart. The HDA device occupies slot 4, so the usual layout is slots 2, 5 and 6 for `WIN11IOS01`, `WIN11INST` and `WINIOSLOG`. The ROM, the UEFI variable store and the on-disk EFI partitions use different backing storage.

The host regression test reproduced an inherited NVMe defect. With two submission queues sharing a two-entry completion queue, two additional reads could overwrite the unread completion of the first read. The old controller drained submissions even with no CQ space, ignored completion DMA failures and published the phase bit together with the payload. The repair waits for the CQ head doorbell, resumes the associated queues and publishes the phase bit after the payload. It also clears the queue state on board warm restart. These are confirmed controller defects. A physical trace is still required to tie the reported stall to one of them or to missing interrupts, host filesystem latency or guest volume handling.

PCI BAR access acquires the machine device lock before the controller mutex, then acquires the GIC lock when signaling an interrupt. The controller still performs positional file I/O synchronously under those locks. Valid NVMe DMA is confined to guest RAM, which prevents re-entry through MMIO. A controller stalled in host I/O can delay other emulated devices. The iOS guest Flush policy defaults to deferred host file checkpoints as it did upstream. Checkpoints are serialized on the host and run separately from diagnostic sampling. NVRAM now reports short or failed writes, requires a writable backing file and participates in host checkpoints. Its errors are recorded separately from disk requests.

## Henge comparison

Henge's `InstallView.swift`, `Installer.swift`, `RangedDownload.swift` and `Machines.swift` show persisted machine folders, HTTP range recovery, sparse disks and progress from a guest restore protocol. Its restore is Apple IPSW and DFU based and uses `idevicerestore`. Windows needs the independent WinPE path described above.

Henge's `JITSetup.swift`, `JITBuiltIn.swift`, `JITPairing.swift` and `HengeJITHelper` coordinate authorized pairing and debugging using an app extension, StikJIT, a Rust pairing library, LocalDevVPN and OS-specific service discovery. ## Managed machine and media compatibility

- Import a folder with `code.fd`, `vars.fd` and either `windows11.img` or `windows11.hvsparse`. Single-file IMG, RAW and HVSPARSE imports use the bundled firmware and create a fresh writable variable store. Use a complete VM backup when recovering TPM-backed Windows state. Managed prepared images must use 512-byte NVMe sectors and have a valid GPT and EFI system partition. This checks the disk layout. Guest architecture, build and Windows health still require boot.
- New installations default to checksum-pinned QEMU 10.2.0 ArmVirt firmware and Microsoft-attested virtio-win 0.1.285 Windows 11 ARM64 NetKVM. Advanced Settings accepts a compatible firmware pair and an alternative NetKVM folder. Manual firmware validation checks ARM firmware volume headers at offset 0 or 4096 and variable-store headers at offset 0. Windows Setup is responsible for validating network driver package membership and trust.
- The UIKit document picker opens selected documents in place and retains the scoped URL during background coordination. Downloads and Virtual Machines also detect files in Documents/Imports. Pairing-file checks validate record structure locally. The external debugger still performs pairing and JIT activation.
- ISO validation, WinPE extraction and installer disk creation share a read-only reader. It tries UDF, Joliet and ISO9660 in that order and requires an ARM64 EFI loader, BCD, boot.wim and one install.wim or install.esd. Joliet and ISO9660 support streaming multi-extent payload files. The metadata checker rejects split WIM/ESD containers, unsupported XML resource encodings and images outside ARM64 build 26100.
- Microsoft’s 24H2 ARM64 evaluation ISO uses UDF physical partition 2989. libudfread 1.2.0 insists on partition 0 and fails to read its volume descriptor sequence. The pinned upstream revision accepts the actual partition and checks it against the logical volume map. The ISO9660 view on this disc contains a UDF-reader notice. It cannot serve as a source of Windows Setup files.
- The app hashes the complete file before examining its filesystem. A supplied SHA-256 must match. With no reference, the app records the calculated digest for later comparisons and diagnostics. A rejected download stays on device for export or revalidation.
- An ISO can carry install.esd. For a standalone full-distribution ESD, the upstream desktop provisioning script extracts EFI and BCD from index 1, exports WinPE from index 2 and exports the chosen edition into a WIM. Native use of that approach needs index discovery, architecture and build checks, and staging through wimlib. A payload-only ESD lacks the EFI and WinPE files needed by the on-device installer. Standalone ESD import is pending.
- The draft stores the Windows ISO identifier and a stable machine identifier. If app termination interrupts disk preparation, reopening the wizard lets the user retry without downloading the same media. Background downloads use operating-system recovery and retain resume data when available. An expired link or a source without resume support can require starting over.

## Experimental JIT sizing

JIT capacity and offsets use 64-bit `size_t` and `intptr_t` on iOS. At 1536 MiB the existing capacity rule gives about 10.1 million block slots and twice as many chain slots, within the 32-bit counters. These tables increase virtual and potentially resident memory. Intra-block hot/cold branches stay in the existing 1 MiB per-CPU chunks. The dispatcher checks signed AArch64 branch reach before direct chaining and retains the indirect path for far targets. Guest RAM and physical addresses are 64-bit, and the 10 GiB guest layout stays below high ECAM. These are static checks. They establish neither sufficient device VM space nor stable resident memory under real load.

## TPM and Secure Boot

New Setup sessions present a TPM 2.0 FIFO device using libtpms. The ARM64 device tree includes `tcg,tpm-tis-mmio`, and ACPI includes a `TPM2` table and `MSFT0101` device. Existing prepared guests keep their prior TPM configuration. The library stores device state per VM, rejects corrupt state, and saves TPM-backed VM backups locally on the device. The bundled QEMU variable template starts with its stock enrollment state. Users needing pre-enrolled Secure Boot keys can provide a compatible pair in Advanced Settings. Firmware discovery, measured boot, Secure Boot state and Windows acceptance on iPad remain unverified.
