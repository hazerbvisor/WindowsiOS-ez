## Project MetalGPU

`experimental/metal-gpu` begins at UI build `ba7fde7` and inherits the DISM foundation. It adds an opt-in VirtIO-GPU display-only device with control and cursor queues, EDID, scanout, checked RAM transfers, fences, MSI-X/INTx, reset and RAMFB fallback. The existing diagnostics export identifies the framebuffer source and records the 2D device's actual queue, resource and reset counters. A normal launch and installer sessions still use RAMFB.

The host test exercises the PCI identity and BARs through ECAM, malformed ring and command rejection, DMA bounds, resource budgeting, pixel and cursor updates, completion, interrupt masking, and fallback. It passed with AddressSanitizer and UndefinedBehaviorSanitizer. The portable suite ran 34 tests with 33 passes and one skipped opt-in streaming fixture. The genuine LTSC 24H2 ARM64 ISO tests ran. Swift syntax parsing and targeted Clang static analysis passed. The signed Windows driver archives were checked against their published hashes, inspected for ARM64 kernel binaries and verified for catalog signature integrity without Windows trust evaluation. Xcode compilation, Windows driver start, simulator and iPad tests for this branch remain unverified.

The session toolbar now has a dedicated hide action. Session Details opens Windows Settings for guest resolution selection where the adapter exposes multiple modes. The processor picker and native engine accept 1–8 vCPUs, with 5–8 marked experimental. Host tests check the saved counts and the firmware's four- and eight-processor tables. Run these changes on-device using [TESTING.md](TESTING.md).

The first hardware gate is PCI enumeration and recovery on a copied Windows VM. The accelerated adapter needs a shared-memory PCI aperture, context and blob commands, async fences and the pinned Neptune + DXMT backend. The current Metal presenter displays 2D scanout pixels and exposes no Direct3D capability. Madeira development starts after demonstrated and stable Direct3D 11. ### Black-screen investigation from 7b944127

The iPad report showed 821 presented drawables, 351/351 retired VirtIO fences, GL errors 1282 and 1286 in VirGL context 6, and an illegal GL fence. The pinned renderer's poll path waits from ctx0 and treats `GL_WAIT_FAILED` as a retirement. Its ordinary GL callbacks and external surfaceless callbacks use separate creation paths. The previous fix only joined the surfaceless path to the app's root. WindowsiOS still created ctx0 with no shared context. That split violates the renderer's shared-resource and sync assumptions and explains how GL rendering can fail while the presenter continues to submit frames. The new adapter shares the same root for ctx0 and all children and probes a shared texture, a complete framebuffer and a cross-context GL fence during initialization. A new iPad run will establish whether this fixes the reported freeze.

The lab GPU now serves the pinned driver's pre-negotiation EDID request when EDID is advertised, matching the reference QEMU handler. Diagnostics record the actual negotiated bit, compatibility responses and fence reply errors separately. Session Details offers an optional CPU-readback diagnostic on the native scanout path. It blits the current Metal texture, measures its RGB data after completion, then uploads a separate texture for display. It exports aggregate counts without exporting pixels. No Windows changes are required.

An iPad retest of the readback build still showed the original display symptom. Its log recorded `angle_share_verified=1`, one successful EDID compatibility response, and no repeat of the earlier GL or illegal-fence warnings during the captured interval. The device retired 285 of 285 fences with zero reply errors and presented 645 drawables. CPU readback was off, so the report provides no pixel data about the active scanout. The remaining cause is open. A readback capture from the same session and a comparison with the direct display are needed to decide which path to investigate next.

A second physical iPad capture enabled CPU readback during the failure. It measured 51 of 51 black frames, zero changes and zero readback errors. The renderer had retired 166 of 166 fences and the presenter had presented 1,087 drawables without reporting an error. The scanout texture supplied to the Metal presenter contained black RGB data when sampled. The captured interval still had successful ANGLE sharing and an EDID compatibility reply. The remaining cause is unresolved.

The same diagnostic toggle now samples the current renderer resource independently of the Metal presenter. Typed VirGL scanouts use a bounded GLES transfer read. Neptune shared-memory scanouts read bounded tiles from the exported backing file. The report identifies the selected resource and scanout command and counts black tiles, nonblack tiles and errors. Producer samples are limited to nine small tiles per activation and require an idle control queue with no outstanding deferred fences. No guest pixels are exported. Linux tests exercised the shared-memory reader and pixel classification. The paired GLES/Metal measurement on the iPad remains unverified.
